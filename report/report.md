## 1. Введение и постановка задачи

Цель проекта: предсказать, будет ли возвращен товар после покупки.
Это задача бинарной классификации, где:

- `returned = 0` означает, что товар не был возвращен;
- `returned = 1` означает, что товар был возвращен.

Такая модель полезна для e-commerce по нескольким причинам:

- можно заранее оценивать риск возврата;
- можно искать проблемные категории товаров и способы доставки;
- можно оценивать финансовые потери от возвратов;
- можно использовать предсказание в аналитике, скоринге заказов и дальнейшем продукте.

Основная метрика качества для проекта на CP1: `ROC-AUC`.
Я выбрал ее, потому что в задаче важно получить и бинарный ответ и
ранжировать заказы по вероятности возврата. Дополнительно я смотрю на `PR-AUC`,
`F1`, `precision`, `recall` и `accuracy`.

### 3.1 Пропуски и дубли

Проверка `train.csv` показала:

- пропусков: `0`;
- полных дублей: `0`.

Несмотря на отсутствие пропусков в текущей версии датасета, в пайплайн модели
добавлены `SimpleImputer` для числовых и категориальных признаков, чтобы запуск
оставался устойчивым на новых данных.

### 3.2 Невалидные значения и выбросы

В датасете есть значения, которые противоречат смыслу признаков.

| Проверка                     | Количество строк |
|------------------------------|-----------------:|
| `product_price < 0`          |            27285 |
| `num_product_views < 0`      |            21443 |
| `product_rating < 1`         |            14280 |
| `product_rating > 5`         |             3831 |
| `past_return_rate < 0`       |             2220 |
| `discount_percent < 0`       |             1686 |
| `session_length_minutes < 0` |             1487 |

Стратегия обработки:

- для каждого типа аномалии создается бинарный флаг `invalid_*`;
- сами значения клипуются к допустимому диапазону;
- строки не удаляются, чтобы не терять слишком много наблюдений.

Это решение кажется мне разумным для CP1: модель получает и очищенное значение,
и информацию о том, что в исходных данных была аномалия.

### 3.3 Feature engineering

До feature engineering в модели было `14` исходных признаков.
После preprocessing получается `25` модельных признаков.

Добавленные признаки:

| Признак                 | Смысл                                    |
|-------------------------|------------------------------------------|
| `price_after_discount`  | цена после скидки                        |
| `discount_amount`       | абсолютный размер скидки                 |
| `views_per_minute`      | интенсивность просмотра товара           |
| `high_past_return_rate` | флаг высокой исторической доли возвратов |
| `has_discount`          | флаг наличия скидки                      |
| `invalid_*`             | флаги исходных невалидных значений       |

EDA выполнен в ноутбуке [`notebooks/01_eda.ipynb`](../notebooks/01_eda.ipynb).

В ноутбуке построены:

- часть числовых признаков содержит очевидные аномалии, поэтому очистка обязательна.

### 3.5 Train/validation/test split и защита от data leakage

Для локальной проверки используется стратифицированный split:

- train: `140000` объектов;
- validation: `30000` объектов;
- test: `30000` объектов.

Доля положительного класса одинаковая во всех частях:

- train: `0.4746`
- validation: `0.4746`
- test: `0.4746`

Как избегалась утечка:

- `order_id` исключен из признаков как технический идентификатор;
- preprocessing и one-hot encoding обучаются только на train внутри `Pipeline`;
- `test.csv` с Kaggle не участвует в локальной оценке качества, потому что в нем нет таргета.

## 4. Baseline-модель

В качестве baseline используется `logistic_regression_baseline`.
Это простая модель без feature engineering: на вход подаются только исходные
признаки после стандартного препроцессинга в sklearn-пайплайне.

Для сравнения я также оставил нижнюю границу качества:

- `dummy_most_frequent`, которая всегда предсказывает самый частый класс.

Результаты baseline на validation:

| Модель                         | ROC-AUC | PR-AUC |     F1 | Precision | Recall | Accuracy |
|--------------------------------|--------:|-------:|-------:|----------:|-------:|---------:|
| `dummy_most_frequent`          |  0.5000 | 0.4746 | 0.0000 |    0.0000 | 0.0000 |   0.5254 |
| `logistic_regression_baseline` |  0.5866 | 0.5550 | 0.5499 |    0.5372 | 0.5632 |   0.5624 |

Вывод по baseline:

- даже простая логистическая регрессия сильно лучше dummy-модели;
- в датасете есть сигнал, достаточный для осмысленного обучения уже на CP1.

## 5. Эксперименты

Полная таблица результатов лежит в [`report/cp1_experiments.csv`](cp1_experiments.csv).

### Эксперимент 1

Гипотеза: простой baseline без feature engineering уже даст заметный выигрыш
относительно dummy-модели.  
Как проверялось: обучена `logistic_regression_baseline`.  
Результат: `ROC-AUC = 0.5866` против `0.5000` у dummy.

### Эксперимент 2

Гипотеза: engineered-признаки улучшат линейную модель.  
Как проверялось: обучена `logistic_regression_features` с признаками
`price_after_discount`, `discount_amount`, `views_per_minute`,
`high_past_return_rate`, `has_discount` и `invalid_*`.  
Результат: улучшение небольшое, но есть: `ROC-AUC = 0.5875` против `0.5866`.

### Эксперимент 3

Гипотеза: дерево решений повысит recall за счет нелинейных зависимостей.  
Как проверялось: обучена `decision_tree_depth6`.  
Результат: recall вырос до `0.6267`, но итоговый `ROC-AUC = 0.5747`, что хуже
логистической регрессии.

### Эксперимент 4

Гипотеза: random forest лучше поймает нелинейности и даст лучший `ROC-AUC`.  
Как проверялось: обучена `random_forest_depth12` с `100` деревьями.  
Результат: лучшая модель на validation, `ROC-AUC = 0.5915`.

## 6. Финальная модель и интерпретируемость

На текущем этапе в качестве лучшей модели CP1 выбрана `random_forest_depth12`.
На внутреннем test split она показала:

- `ROC-AUC = 0.5888`
- `PR-AUC = 0.5597`
- `F1 = 0.5419`
- `Precision = 0.5345`
- `Recall = 0.5494`
- `Accuracy = 0.5591`

Почему выбрана именно она:

- у нее лучший `ROC-AUC` на validation;
- качество на test близко к validation, то есть сильного провала нет;
- модель уже лучше простой линейной baseline.

Наиболее важные признаки по feature importance у random forest:

1. `delivery_delay_days`
2. `session_length_minutes`
3. `past_return_rate`
4. `discount_percent`
5. `product_rating`
6. `discount_amount`
7. `product_price`

Это выглядит правдоподобно: на возвраты действительно могут влиять задержка
доставки, предыдущая история возвратов, скидка и свойства товара.
