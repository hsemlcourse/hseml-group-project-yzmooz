## 1. Введение и постановка задачи

Цель проекта: предсказать, будет ли возвращен товар после покупки.
Это задача бинарной классификации, где:

- `returned = 0` означает, что товар не был возвращен;
- `returned = 1` означает, что товар был возвращен.

Такая модель полезна для e-commerce по нескольким причинам:

- можно заранее оценивать риск возврата;
- можно искать проблемные категории товаров и способы доставки;
- можно оценивать финансовые потери от возвратов;
- можно использовать предсказание в аналитике, скоринге заказов и дальнейшем продукте.

Основная метрика качества для проекта на CP1: `ROC-AUC`.
Я выбрал ее, потому что в задаче важно получить и бинарный ответ и
ранжировать заказы по вероятности возврата. Дополнительно я смотрю на `PR-AUC`,
`F1`, `precision`, `recall` и `accuracy`.

## 2. Поиск и описание данных

Источник данных: https://www.kaggle.com/datasets/hakdevelopment/e-commerce-dataset.
Нашел датасет на kaggle, тк это крупнейшая международная онлайн-платформа и сам датасет идеально подходит под задачу.
Почему выбран именно этот датасет:

- он напрямую соответствует выбранной теме проекта;
- в нем есть и клиентские, и товарные, и транзакционные признаки;
- размер датасета подходит под требования курса;
- задача естественно формулируется как ML-классификация, а не просто EDA.

В проекте используются три файла:

| Файл                    |  Строк | Колонок | Назначение                  |
|-------------------------|-------:|--------:|-----------------------------|
| `train.csv`             | 200000 |      16 | обучение и локальная оценка |
| `test.csv`              |  50000 |      15 | внешний тест без таргета    |
| `sample_submission.csv` |  50000 |       2 | шаблон ответа для Kaggle    |

Основной файл для обучения: `train.csv`.

Состав признаков в `train.csv`:

- 14 содержательных признаков;
- `order_id` как технический идентификатор;
- `returned` как целевая переменная.

Распределение классов:

| Класс          | Количество |   Доля |
|----------------|-----------:|-------:|
| `returned = 0` |     105081 | 52.54% |
| `returned = 1` |      94919 | 47.46% |

Классы достаточно близки по размеру, поэтому задача не является сильно
дисбалансированной.

## 3. Обработка и подготовка данных

Весь preprocessing вынесен в код:

- [`src/preprocessing.py`](../src/preprocessing.py)
- [`src/prepare_data.py`](../src/prepare_data.py)

### 3.1 Пропуски и дубли

Проверка `train.csv` показала:

- пропусков: `0`;
- полных дублей: `0`.

Несмотря на отсутствие пропусков в текущей версии датасета, в пайплайн модели
добавлены `SimpleImputer` для числовых и категориальных признаков, чтобы запуск
оставался устойчивым на новых данных.

### 3.2 Невалидные значения и выбросы

В датасете есть значения, которые противоречат смыслу признаков.

| Проверка                     | Количество строк |
|------------------------------|-----------------:|
| `product_price < 0`          |            27285 |
| `num_product_views < 0`      |            21443 |
| `product_rating < 1`         |            14280 |
| `product_rating > 5`         |             3831 |
| `past_return_rate < 0`       |             2220 |
| `discount_percent < 0`       |             1686 |
| `session_length_minutes < 0` |             1487 |

- создаётся бинарный флаг `invalid_*`;
- значение клипуется до допустимого диапазона;
- строка не удаляется, чтобы не терять наблюдения.

Feature engineering добавляет:

| Признак                 | Смысл                                  |
|-------------------------|----------------------------------------|
| `price_after_discount`  | цена после скидки                      |
| `discount_amount`       | абсолютный размер скидки               |
| `views_per_minute`      | интенсивность просмотра товара         |
| `high_past_return_rate` | высокий исторический процент возвратов |
| `has_discount`          | наличие скидки                         |
| `invalid_*`             | флаги исходных невалидных значений     |

После preprocessing число модельных признаков увеличивается с `14` до `25`.

Для локальной оценки используется stratified split:

- train: `140000` объектов;
- validation: `30000` объектов;
- test: `30000` объектов.

Защита от data leakage:

- `order_id` исключён из признаков;
- imputation, scaling и one-hot encoding обучаются только на train внутри
  `Pipeline`;
- Kaggle `test.csv` без таргета не участвует в подборе модели.

## 4. Baseline

Baseline - `logistic_regression_baseline` без feature engineering. Он нужен как
референс, чтобы сравнить CP2-модели с простой моделью.

Validation-результат baseline:

| Модель                         | ROC-AUC | PR-AUC |     F1 | Precision | Recall | Accuracy |
|--------------------------------|--------:|-------:|-------:|----------:|-------:|---------:|
| `logistic_regression_baseline` |  0.5866 | 0.5550 | 0.5499 |    0.5372 | 0.5632 |   0.5624 |

## 5. Эксперименты CP2: перебор гиперпараметров

Главное изменение CP2 - системный перебор гиперпараметров через
`sklearn.model_selection.ParameterGrid`. Все tuned-модели обучались с feature
engineering, а лучшая модель выбиралась только по validation `ROC-AUC`.

Сетки гиперпараметров:

| Семейство                | Перебираемые параметры                                                             |
|--------------------------|------------------------------------------------------------------------------------|
| `LogisticRegression`     | `C=[0.3, 1.0, 3.0]`, `class_weight=[None, "balanced"]`                             |
| `DecisionTreeClassifier` | `max_depth=[4, 8, 12, None]`, `min_samples_leaf=[50, 200]`                         |
| `RandomForestClassifier` | `n_estimators=[100, 200]`, `max_depth=[8, 12, None]`, `min_samples_leaf=[20, 100]` |
| `ExtraTreesClassifier`   | `n_estimators=[100, 200]`, `max_depth=[8, 12, None]`, `min_samples_leaf=[20, 100]` |

Всего проведено `39` validation-запусков: baseline и `38` конфигураций grid
search. Полная таблица сохранена в `report/cp2_experiments.csv`.

Лучшие validation-результаты по семействам:

| Лучшая модель семейства        | Параметры                                                  | ROC-AUC | PR-AUC |     F1 | Precision | Recall | Accuracy |
|--------------------------------|------------------------------------------------------------|--------:|-------:|-------:|----------:|-------:|---------:|
| `random_forest_grid_08`        | `max_depth=12`, `min_samples_leaf=100`, `n_estimators=200` |  0.5922 | 0.5594 | 0.4705 |    0.5618 | 0.4047 |   0.5677 |
| `logistic_regression_grid_02`  | `C=0.3`, `class_weight="balanced"`                         |  0.5875 | 0.5557 | 0.5500 |    0.5360 | 0.5647 |   0.5614 |
| `extra_trees_grid_05`          | `max_depth=12`, `min_samples_leaf=20`, `n_estimators=100`  |  0.5868 | 0.5535 | 0.4751 |    0.5575 | 0.4139 |   0.5659 |
| `logistic_regression_baseline` | без feature engineering                                    |  0.5866 | 0.5550 | 0.5499 |    0.5372 | 0.5632 |   0.5624 |
| `decision_tree_grid_04`        | `max_depth=8`, `min_samples_leaf=200`                      |  0.5755 | 0.5403 | 0.4900 |    0.5414 | 0.4475 |   0.5579 |

Вывод по экспериментам: лучший результат дала не самая глубокая конфигурация
Random Forest, а ограниченный лес с `max_depth=12` и `min_samples_leaf=100`.
Это похоже на более устойчивую модель: она лучше ранжирует объекты по риску
возврата и не уходит в переобучение на слишком мелких листьях.

## 6. Финальная модель

Финальная модель выбрана строго по validation `ROC-AUC`:

- модель: `random_forest_grid_08`;
- `max_depth = 12`;
- `min_samples_leaf = 100`;
- `n_estimators = 200`;
- файл модели: `models/cp2_best_model.joblib`.

Test split использовался один раз после выбора лучшей конфигурации.

Финальная test-оценка:

| ROC-AUC | PR-AUC |     F1 | Precision | Recall | Accuracy |
|--------:|-------:|-------:|----------:|-------:|---------:|
|  0.5922 | 0.5615 | 0.4722 |    0.5644 | 0.4059 |   0.5694 |

По сравнению с CP1 test `ROC-AUC = 0.5888`, CP2-модель подняла test ROC-AUC до
`0.5922`. Улучшение небольшое, но оно получено не ручным выбором одной модели, а
через системный перебор гиперпараметров.
